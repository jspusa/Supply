# Release the Supply and FBA product catalog

Run one **Product Catalog Release** while preserving two independently deployed sites.

## Resolve the release inputs

1. Use an exact workbook path supplied by the user. Otherwise inspect only likely product-information `.xlsx` files in Downloads and choose the uniquely newest file whose workbook contains `AMZ 所有SKU`, `2026`, or `罐頭`; ask when the candidate is ambiguous.
2. Locate the sibling `jspusa/Supply` and `jspusa/FBA` clones, then validate `package.json` and Git remotes instead of trusting a machine-specific path.
3. Read Supply's `AGENTS.md`, `CONTEXT.md`, and applicable catalog ADRs. Read the available GitHub publication skill before remote operations.

The existing raw workbook is the maintained input. Keep it local, add no maintenance worksheets, and stage only allowlisted generated catalog artifacts. Either public site's Product Update Entry may read that raw workbook directly, but only in tab memory: it must not persist raw bytes, the signed plan, or review selections to localStorage, sessionStorage, or IndexedDB. Reload clears them. The site has no repository credentials or write path.

## Plan before writing

The normal review path is: open Product Update Entry in Supply or FBA, select the raw workbook, review the generated risk inbox, download the signed Catalog Change Plan, explicitly select any approved high-risk entries, and download the compact selection handoff. Blank raw cells preserve canonical facts. Use the per-SKU/per-field **explicit clear** controls only when Jasper really intends data loss; each clear must regenerate and re-sign the plan and remain review-risk/unselected.

The raw workbook does not provide a trustworthy product name or order-unit mode. For an unseen SKU, keep `productName` empty, `orderUnit` null, and lifecycle incomplete; never substitute the SKU as a name or assume single/1. It may retain sufficient FBA packaging history, but it stays out of new Supply work until real product and order-unit facts exist. An explicit Alias carton clear preserves owner identity and immutable historical versions while making the incomplete default ineligible for new Supply/FBA work.

Supply remains the canonical owner. FBA uses Supply-generated byte-identical local planner modules and a public-sanitized local baseline; neither site fetches the other site's full catalog at runtime.

For a CLI-only report, require clean worktrees and current default branches. From Supply run:

```bash
npm run catalog:release -- --input <raw.xlsx> --fba-repo <FBA-path> --report <temporary-report.json>
```

Read the signed report and account for every changed Product SKU and Order SKU Alias. Report units per carton, dimensions, carton weight, cartons per pallet, lifecycle, factory, alias owner, source evidence, and affected work as old → new. Safe changes start selected; factory, origin, lifecycle, alias-owner, and explicit-clear changes require a separate selection after review. Stop before applying when:

- there are no public product changes;
- any source conflict lists competing complete values;
- any entry is removed;
- an approved alias owner or other high-risk fact changed without the user's explicit selection;
- an active product becomes incomplete without an explicitly reviewed clear that necessarily causes that lifecycle change;
- either worktree is dirty, behind its remote default branch, or contains unrelated changes.

Complete duplicate rows may merge only when their public values agree. Competing complete rows block the release with every sheet, row, and value shown; never choose the first or last row. Never infer a 7-prefixed alias owner.

## Apply and verify

Create the same versioned feature branch in both repositories. Use the exact plan file that was reviewed; add one `--select <entry-id>` per explicitly approved high-risk change, or use the selection handoff downloaded after reviewing that exact plan in either site's Product Update Entry. Then run:

```bash
npm run catalog:release -- --input <raw.xlsx> --fba-repo <FBA-path> --apply --reviewed-plan <temporary-report.json> --verify [--select <entry-id>]
```

For a Product Update Entry handoff, replace the bracketed `--select` arguments with `--selection-handoff <selection.json>`. Never combine the two. When `--version` is omitted, the local tool derives it from the reviewed plan, rereads the raw workbook, and must match the public-sanitized baseline/candidate hashes, entries, source evidence, and `planSha256` before honoring exact selected IDs. It separately validates the full canonical schema and immutable history.

The apply step must reread the raw workbook and reject a stale baseline, candidate hash, plan signature, or conflicting source. Released packaging history is immutable: a correction appends a Packaging Specification Version and changes only the new-work default; it never rewrites a version already assigned to an Order Draft or FBA inbound/expiry row.

Completion permits only these release-owned paths:

- Supply: canonical catalog, generated Supply snapshot, public-sanitized Catalog Update runtime projection, compact Catalog Alignment manifest, public Catalog Change Record, and local Catalog Alignment evidence record.
- FBA: generated FBA snapshot/HTML, the byte-identical local Catalog Update runtime projection, and compact Catalog Alignment manifest.

Review and stop on any additional path. Run Supply's browser suite separately when the environment needs permission to bind its local test server.

If the user explicitly requested publication or going live, read [references/publish.md](references/publish.md) and continue. Otherwise stop after the verified local plan or apply result without remote writes.

## Completion

Report the raw workbook basename, catalog version, every selected and skipped old → new SKU change, packaging-version effect, both test results, both pull requests when created, and stage-specific Catalog Alignment evidence. A green workflow without matching live public hashes and browser behavior is incomplete. A partial two-repository release remains visibly failed, blocks the next catalog version, and is repaired by retrying only the failed site—never by silently rolling back or overwriting the successful site.
